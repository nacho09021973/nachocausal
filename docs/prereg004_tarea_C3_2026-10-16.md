## ⚠ La GPU NVIDIA no se puede usar para C3

El prerregistro congelado fija C3 en CPU (`gpu_dev_only`, comité 052; `docs/preregistration_004.md`
§3). El código lo impone: `thresholds.assert_environment` aborta si CuPy está cargado o si
`NC2P1_DEVICE` no es `cpu`. Correr C3 en GPU exigiría un prerregistro nuevo.

La GPU sí puede servir **antes** de C3, fuera del camino ciego, solo con semillas de exploración
ya quemadas. Por ejemplo, para regenerar con `dev/gen2p1_gpu.py` el registro GPU de la semilla
`7_000_100` y compararlo con la CPU del equipo nuevo (paso 2). No es necesario, porque ese
registro ya está en `dev/2p1_sweep_T_rho126_v2_2026-10-12.jsonl`.

## Cambio de equipo: qué implica

- El §8 midió en un i7-13700 con WSL2, 20 hilos de numba y 20 CPUs visibles. Otro equipo es
  una configuración no medida. El §9 ya lo dice: «Bit-reproducibility is claimed only for 20 numba
  threads on the measured host (§8); a run elsewhere is unverified». Hay que declararlo en el
  documento de resultado.
- C3 exige exactamente 20 hilos de numba (`assert_blind_threads`). El equipo debe tener al menos
  20 CPUs lógicas visibles. No se cambia el número de hilos: está congelado.
- Entorno fijado exacto: Python 3.12.3, numpy 1.26.4, numba 0.66.0, llvmlite 0.48.0, scipy 1.17.1
  (`requirements-lock.txt`). Si no coinciden, `assert_environment` aborta antes de generar nada.

## Pasos

1. **Preparar el equipo** (reversible).
   - Clonar el repo y hacer `git fetch`. Comprobar que `origin/prereg004/step3-port` contiene
     `8ff5b3b` y el commit de esta nota.
   - Crear `.venv` con Python 3.12.3: `python3.12 -m venv .venv && .venv/bin/pip install -r requirements-lock.txt`.
   - `nproc` ≥ 20. En WSL, `processors` en `.wslconfig` ≥ 20 y después `wsl --shutdown`.
   - Que no exista `results/validation_004.json` en el equipo. La unicidad de la corrida depende
     de esto y del registro en git.
2. **Comprobaciones previas** (reversibles, sin semillas vírgenes), con `PY=.venv/bin/python`:
   - `make verify-seal PY=$PY` → `6e2c3888…`;
   - `make verify-seal-004` → igual a la tabla §3 de `docs/preregistration_004.md`;
   - `make test-004 PY=$PY` y `make test PY=$PY` (560 aprobados en el equipo anterior);
   - `NUMBA_NUM_THREADS=20 make dry-run-004 PY=$PY`.
   - Recomendado por el cambio de equipo: paridad con el registro GPU en la semilla quemada
     `7_000_100`, ρ = 126, T = 16. Comando:
     `NUMBA_NUM_THREADS=20 $PY dev/preflight_2p1.py --seeds 7000100 --out dev/preflight_2p1_<equipo>_2026-10-16.jsonl`.
     Deben coincidir los 15 campos, como en `dev/PREREG004_STEP_5_2026-10-13.md`; tarda unos
     10 min. Commit del jsonl en la rama. **Si no coincide, no se lanza C3: se para y se consulta
     al PI.**
3. **Situarse en el commit de C2.** El §9 dice que C3 usa el commit C2 publicado como HEAD:
   `git checkout --detach 8ff5b3b`, con `git status --porcelain` vacío.
4. **Fichero de procedencia.** Ejecutar en bash, desde la raíz, el bloque del §9 de
   `docs/preregistration_004.md` con `PY=.venv/bin/python` y
   `C1=d6494e5aa32289594c1f30033ac041eecdb87ee6`. Debe dar `sealed_diff_lines 0` y
   `status_porcelain_lines 0`; si no, no se lanza.
5. **Lanzar C3, una sola vez**, en la misma shell (con `NUMBA_NUM_THREADS=20` ya exportado):
   `nohup $PY -m nachocausal2p1.validate > results/validation_004_run.log 2>&1`.
   Al terminar: `echo "end_utc $(date -u +%FT%TZ)" >> results/validation_004_provenance_launch.txt`.
   - Mantener el equipo despierto. Duración estimada con 20 hilos: unas 4,4 h `[UNVERIFIED]`;
     en otro equipo puede variar.
   - Caída sin salida de puntuación: se relanza con las mismas semillas, el mismo entorno y el
     mismo commit, y se registra. Un aborto determinista (`ABORTED_GUARD_V`,
     `ABORTED_TAU_RANGE`) no se relanza.
6. **Registrar inmediatamente.**
   - `git checkout prereg004/step3-port`. `results/` está ignorado, así que los ficheros se
     conservan al cambiar de rama.
   - `git add -f` de `results/validation_004.json`, `results/validation_004.progress.jsonl`,
     `results/validation_004_provenance_launch.txt` y `results/validation_004_run.log` (los que
     existan).
   - En el mismo commit, `docs/preregistration_004_result.md` con:
     - el veredicto tal cual;
     - las líneas de `sha256sum` de esos ficheros;
     - el equipo usado y la declaración de configuración no medida;
     - bajo INCONCLUSIVE, los valores no vinculantes de cada cláusula del §7.
   - Push.
7. **Informar igual** PASS, FAIL, INCONCLUSIVE u OUT_OF_DOMAIN (§9). No se ajusta nada después
   del resultado, no se repite con otras semillas y no se toca θ.
